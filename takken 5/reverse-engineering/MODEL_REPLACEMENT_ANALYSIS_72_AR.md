# تحليل استبدال موديلات الشخصيات — المرحلة 72

التاريخ: 2026-10-23
المشروع: Wrestling Empire Android 1.8.0 فقط.

## 1. التقدم في فك سجل Costume
أعيد فحص البيانات الفعلية داخل `datapack.unity3d`، وظهر وصف/Type Tree صريح لسجل `Costume` يحتوي الحقول التالية بالترتيب:

`id`, `charID`, `limb`, `texture`, `r`, `g`, `b`, `flesh`, `shape`

وهذا مهم لأننا لم نعد نعتمد فقط على تعريف `Costume` في IL2CPP؛ نفس بنية البيانات تظهر داخل البيانات المعبأة للعبة.

## 2. النتيجة المرتبطة بالـshape
المجموعة المستخدمة في `shape[3]` من بيانات الأزياء التي تم استخراجها سابقًا هي القيم المتصلة `0..14`، أي 15 قيمة.

وفي حزمة `assets/costumes` توجد 15 Mesh للرأس بالضبط.

هذا يحافظ على فرضية قوية:

`Costume.shape[3] -> Head selector -> Head Mesh`

لكن لا يتم اعتماد أي جدول مثل `0=Head_Giant` حتى يتم إثبات الـID الداخلي.

## 3. نقطة مهمة من الفحص الحالي
ظهور Type Tree لسجل `Costume` بجانب البيانات المسلسلة يوضح أن الخطوة الصحيحة التالية هي قراءة **بيانات الكائنات نفسها** وفق الـType Tree، بدل محاولة استنتاج الربط من ترتيب أسماء الـmanifest.

الهدف المباشر هو استخراج مجموعة السجلات التي تحتوي على `shape` ثم ربطها بـObject/Asset references الخاصة بحزمة `costumes`.

## 4. مسار الإثبات المطلوب
1. تحديد بداية بيانات كل Costume object.
2. قراءة عناصر `shape` كـarray وفق SerializedFile format.
3. استخراج أي PPtr/Object reference مرتبط بقيمة الجزء أو الـselector.
4. مقارنة المرجع مع Mesh objects في `CAB-4804a9fe55f251a9b5aff63c07138759`.
5. بناء جدول نهائي: `shape index -> Mesh name`.

إذا لم يوجد PPtr مباشر، سيتم تتبع استخدام الرقم داخل `MHEFCABLLCN` للوصول إلى مفتاح `Resources.Load`.

## 5. ما لم يتم ادعاؤه
لم يتم بعد إثبات أسماء الرؤوس المقابلة لكل رقم 0..14.
لم يتم تعديل APK أو AssetBundle.
لم يتم استخراج Mesh إلى صيغة بديلة أو استبدالها.

## 6. الحالة
- بيانات Character/Costume: ~90%
- بنية Costume/shape: ~85%
- فرضية shape[3] للرأس: ~80%، ما زالت فرضية قوية
- ID -> Head Mesh: ~40%
- بقية أجزاء الجسم: ~30%
- الاستبدال الفعلي: 0%

## الخلاصة
التحليل انتقل من مجرد مطابقة عددية إلى مرحلة قراءة سجل `Costume` وفق بنيته المسلسلة الفعلية. الاختبار التالي الحاسم هو استخراج Object IDs/References المرتبطة بسجلات `Costume` ثم مطابقتها مع Mesh objects، وهو الطريق الأقوى لإثبات جدول الرؤوس قبل أي تعديل.
