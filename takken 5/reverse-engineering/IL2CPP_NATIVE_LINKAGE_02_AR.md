# تقرير ربط Metadata بالملف التنفيذي — الجولة 02

## حالة العمل

هذا التقرير يكمل:
- `STATE_TRANSITION_MAP_01_AR.md`
- `IL2CPP_METADATA_MAP_01_AR.md`

الهدف هو فهم سلوك Wrestling Empire 1.8.0 وبناء مواصفة مستقلة، وليس إعادة نشر الشيفرة الأصلية.

## 1. ما يمكن تأكيده حتى الآن

- اللعبة تستخدم Unity مع IL2CPP بحسب التحليل السابق.
- سجل metadata المتاح أُبلغ أن نسخته 39.
- توجد أسماء مرتبطة بالمقاتل والقتال مثل `Character`, `moveAttack`, `attackViable`, `grapple`, `target`, `distance`, `angleDifference`, `health`, `Stamina`.
- توجد أسماء مرتبطة بالمباراة مثل `Scene_Match_Setup`, `gMatch`, `matchSize`, `winner`.
- توجد أسماء مرتبطة بالحلبة والحبال والكاميرا مثل `ringAnimator`, `ropeAnimator`, `AdjustCamera`, `eventCamera`.

وجود الاسم يؤكد وجود النص/الرمز في البيانات التي فُحصت؛ لكنه لا يثبت وحده أن الاسم Method فعلي أو يحدد عنوان الدالة المنفذة.

## 2. التمييز المهم: ثلاثة أنواع من العناوين

| النوع | ماذا يعني؟ | هل يكفي وحده لتحديد دالة؟ |
|---|---|---|
| String literal address | مكان نص داخل الملف التنفيذي | لا |
| Metadata index/offset | موضع سجل أو اسم ضمن metadata | لا |
| Native method address / RVA | موضع كود الآلة الخاص بالدالة | قد يكفي بعد ربطه بسجل Method الصحيح والتحقق من نوع العنوان |

لا يجوز التعامل مع عناوين النصوص مثل `0x2668878` على أنها عناوين دوال. قد تكون مفيدة للعثور على مراجع النص داخل الملف التنفيذي فقط.

## 3. المسار الصحيح لربط الدوال

1. فحص الملف التنفيذي `libil2cpp.so` وتحديد معمارية ELF ونوعه وخرائط LOAD.
2. استخراج جداول metadata الخاصة بـTypeDefinition وMethodDefinition وFieldDefinition وفق إصدار metadata الفعلي.
3. استخراج أسماء الأنواع والدوال مع token/index وparameter count وreturn/parameter type عندما تكون البيانات متاحة.
4. تحديد آلية تسجيل الدوال في هذا البناء: code registration وmetadata registration أو طريقة الربط التي يستخدمها إصدار Unity هذا.
5. ربط MethodDefinition بالعنوان الأصلي للدالة، مع التمييز بين file offset وRVA وvirtual address.
6. التحقق من عدد محدود من الدوال المرشحة قبل تعميم النتيجة.
7. حفظ جدول نتائج يحتوي على: النوع، اسم الدالة، عدد المعاملات، مصدر الدليل، العنوان ونوعه، ودرجة الثقة.

## 4. أولويات استخراج الدوال

### A. القتال
- `Character` وما يتصل بحالة المقاتل
- `attackViable` و`moveAttack`
- `grapple` و`moveGround`
- `target`, `distance`, `angleDifference`, `victimAngle`
- `health`, `Stamina`, `Strength`, `Skill`

### B. ذكاء الشخصيات NPC
- `Scene_Map`
- `Character`
- `RoadToWrestleManiaMode.StartWinnerPromoDialogue` (اسم مرشح مذكور في تحليل سابق؛ يلزم تأكيده من جدول MethodDefinition قبل اعتباره دالة مؤكدة)
- أي دوال حوار أو قرار أو تفاعل مرتبطة بالشخصية بعد استخراج قائمة الأنواع والدوال الفعلية.

### C. المباراة والخريطة
- `Scene_Match_Setup`
- `gMatch`, `matchSize`, `winner`
- أنظمة الخريطة/المشهد التي تُثبتها قائمة الأنواع والدوال، لا الأسماء النصية وحدها.

## 5. القيود الحالية

لم يُسجَّل في هذا التقرير فحص مباشر جديد لبايتات `libil2cpp.so` أو تنفيذ أداة استخراج على الملف الثنائي؛ لذلك لا أضع عناوين Native أو توقيعات Methods تخمينية. رابط TransferNow الذي أُرسل في المحادثة لم يكن قابلاً للقراءة من أداة الويب في هذه الجولة، وبالتالي لم أتمكن من سحب الملف منه مباشرة.

## 6. الخطوة العملية التالية

يلزم تشغيل محلل على نسختي الملفين المتطابقتين من نفس إصدار اللعبة:
- `global-metadata.dat`
- `libil2cpp.so`

الأفضل أن يعمل التحليل محليًا داخل GitHub Actions بعد توفير الملفين للـworkflow، وأن ينشر نواتج نصية فقط مثل:
- `type_method_catalog.json`
- `combat_method_candidates.csv`
- `npc_dialogue_candidates.csv`
- `elf_layout.txt`

يجب عدم رفع APK كامل أو مفاتيح أو ملفات شخصية إلى الـworkflow. كما ينبغي عدم تضمين شيفرة اللعبة الأصلية في المخرجات.

## 7. معيار نجاح المرحلة

لن تُعتبر المرحلة مكتملة بمجرد العثور على strings. النجاح يعني وجود سجل MethodDefinition صالح، وتوقيع/عدد معاملات متسق، وربط موثّق بعنوان native مع بيان نوع العنوان ومصدره. أما تحليل الضرر وقرارات AI فيظل غير محسوم حتى تتوفر بيانات الدوال أو اختبارات سلوكية قابلة للتكرار.
